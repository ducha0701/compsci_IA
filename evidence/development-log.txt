# Development log

## Dataset inspection, cleaning and feature preparation — 12–13 October 2026

### Objective
Prepare the Kaggle Spotify dataset for use in a music recommendation engine, preserving the original CSV and creating reproducible processing scripts.

### Environment
The project is stored in C:\CS_IA. I created a Python virtual environment using Python 3.14.2 and installed pandas 3.0.6. NumPy 2.5.4 was installed as a dependency. I added .venv/ and __pycache__/ to .gitignore to exclude generated environment files from version control.

### Dataset inspection
I created scripts/inspect_dataset.py to inspect the CSV’s dimensions, column types, sample records, missing values and duplicates.

The dataset contained 114,000 rows and 20 columns. There were 450 exact duplicate rows. One record was missing its artist, album name and track name and also had a duration of zero.

After removing exact duplicates in memory, there were 113,550 rows and 89,741 distinct track IDs. Inspection showed that a track could appear under several genre labels. For example, “Comedy” by Gen Hoshino appeared under acoustic, j-pop, singer-songwriter and songwriter.

I checked whether repeated track IDs had conflicting values in other columns. Popularity differed for 720 track IDs; the other checked columns agreed.

### Cleaning decisions and implementation
I created scripts/preprocess_dataset.py with these rules:

1. Remove records missing track_id, artists or track_name.
2. Remove exact duplicate rows.
3. Group remaining records by track_id.
4. Preserve all distinct genre labels in alphabetical order, separated by semicolons.
5. Average popularity values within each track ID.
6. Retain the first value for other columns because inspection showed those values agreed.

Combining genre labels avoids losing information when consolidating repeated tracks. Averaging popularity is a reproducible compromise because the dataset does not provide timestamps identifying the latest popularity value.

The cleaned dataset was saved separately as data/processed/tracks_cleaned.csv. The original CSV was not modified.

### Cleaning validation
The script reported:
- Original rows: 114,000
- Rows excluded for missing required information: 1
- Exact duplicates removed: 450
- Cleaned tracks: 89,740

Assertions confirmed unique track IDs, no missing required identification fields and preservation of all retained distinct track IDs. A displayed example confirmed that “Comedy” retained all four genre labels.

### Feature preparation
I selected nine initial audio features: danceability, energy, loudness, speechiness, acousticness, instrumentalness, liveness, valence and tempo.

Their original ranges differed substantially. I applied Min–Max scaling to put each selected feature on a range from 0 to 1.

I created scripts/prepare_features.py and saved:
- data/processed/audio_features_scaled.csv
- data/processed/audio_scaling_settings.csv

### Scaling validation
Assertions checked for missing feature values, zero feature ranges, changed row counts and scaled values outside 0–1. All checks passed.

The output contained 89,740 tracks. Every selected feature had a scaled minimum of 0 and maximum of 1.

### Assistance and understanding
Codex provided code examples and explanations. I created and ran the scripts in VS Code and reviewed their outputs. The key distinction I learned was that exact duplicate rows differ from repeated track IDs: repeated IDs can contain useful additional genre labels.

### Limitations and next steps
Recommendation quality has not yet been tested. The feature selection and scaling method are initial choices that may need revision following evaluation. Zero tempo values remain in the dataset and require investigation before deciding whether to treat them differently.

The next implementation step is a small song-to-song similarity baseline, followed by evaluation before adding user preferences, clustering or the web application.

## Dataset replacement and recommendation search — 13–14 October 2026

### Problem identified
The original dataset supported the similarity calculation but lacked several familiar songs. A title-and-artist coverage check found none of my ten test songs. This showed that a working algorithm alone was insufficient: users also need to find songs they know when entering preferences.

### Dataset comparison and decision
I inspected two replacement candidates.

The first, Rodolfo Figueroa’s Spotify 1.2M+ Songs dataset, contained 1,204,025 rows but did not contain my ten test songs. It also lacked genre and popularity columns, so I rejected it as a replacement.

I selected Amitansh Joshi’s Spotify 1 Million Tracks dataset:
https://www.kaggle.com/datasets/amitanshjoshi/spotify-1million-tracks

It contained 1,159,764 unique track IDs, genre labels, popularity and the nine audio features used by my baseline. Four of my ten test songs were found, along with several familiar older songs or remastered versions. This demonstrated improved coverage for the test sample.

### Inspection and cleaning
I created scripts/inspect_candidate.py to check missing values, duplicates, feature ranges and non-finite numerical values.

Inspection found:
- 15 missing artist names.
- One missing track name.
- No missing values in the nine selected audio features.
- No infinite audio feature values.
- No exact duplicate rows after excluding the exported index column.
- Unique track IDs throughout the dataset.

I created scripts/preprocess_new_dataset.py to remove the exported index, rename artist_name to artists and genre to track_genre, strip whitespace from identification fields and exclude records missing required identification.

The column renaming preserved compatibility with the existing recommender. Unlike the original dataset, this candidate did not require grouping repeated track IDs or averaging conflicting popularity values.

### Cleaning validation
The script excluded 16 records and saved 1,159,748 tracks to data/processed_1m/tracks_cleaned.csv.

Assertions confirmed unique track IDs, complete required identification fields, finite audio features and non-missing genre labels.

### Feature scaling
I created scripts/prepare_features_1m.py and recalculated Min–Max scaling using the new dataset’s ranges.

The script retained all 1,159,748 cleaned tracks. Each of the nine selected features had a scaled minimum of 0 and maximum of 1. New scaled features and scaling settings were saved in data/processed_1m/.

### Recommender and search changes
I changed scripts/recommend_similar.py to load the new processed files.

Searching only by title displayed the first 20 matches, which hid the intended “Magnolia” entry. I added an optional artist filter before limiting the displayed results. Searching for “Magnolia” and “Playboi Carti” successfully located the intended track.

### Limitations and evaluation
The replacement improves tested coverage but remains incomplete. Artist-name checks found no entries for Tame Impala, Kanye West, Juice WRLD or Yeat under those names.

The coverage sample reflects my preferences and does not establish coverage for every user. Client-specific coverage and recommendation usefulness still require evaluation. High cosine-similarity scores do not represent a probability that a user will enjoy a song.

17–20 October 2026 — Dashboard song search and rating storage

Objective
Connect the song catalogue to the website and allow authenticated users to save and update song ratings.

Catalogue loading and search
Created catalogue.py to load track_id, track_name and artists from data/processed_1m/tracks_cleaned.csv. Loading only these columns avoids loading unnecessary audio features for searching. A terminal check confirmed 1,159,748 rows and three columns.

Implemented search_songs() with optional title and artist filters. Searches use case-insensitive, literal substring matching. Both filters are applied before limiting results to 20 rows, preventing an intended song from being excluded before artist filtering.

Connected the dashboard GET form to Flask using request.args. Passed query values back to the template so the inputs remain visible after submission. Converted matching DataFrame rows into dictionaries for the template to display.

Search validation and testing
Added separate displays for matching results, no matching songs and invalid search inputs. Empty searches display neither results nor an error.

Searching for “a” in both fields produced overly broad results. Added server-side validation requiring at least one field to contain two or more characters. Invalid searches display a validation message without running the catalogue search.

Tests passed:

Magnolia / Playboi Carti displays the intended song.

A made-up title displays the no-matches message.

Empty fields display neither results nor an error.

One-character inputs in both fields display only the validation message.

A short title can still be searched with a sufficiently specific artist.

Rating form and validation
Added SongRatingForm in forms.py, containing a hidden track_id field, an integer-coerced score dropdown with choices 1–5 and a submit button.

Displayed a separate POST form beside each song result. Each form includes a CSRF token and the corresponding track ID.

Created the /rate route. It checks that the user is logged in and validates the submitted form. Added track_exists() in catalogue.py to reject IDs absent from the catalogue, because hidden form fields can be modified by the browser.

Database storage
Implemented a parameterized INSERT into the ratings table. ON DUPLICATE KEY UPDATE changes the existing rating when the same user rates the same track again.

The user ID comes from the login session rather than a submitted field. The track ID and score come from the validated form.

The transaction commits after successful execution. Errors trigger rollback and are raised again. Cursor and connection cleanup run through finally blocks. The successful redirect is outside finally so it cannot suppress a database error.

Rating tests passed

Submitting a different rating for the same song and account updates that row without creating a duplicate.

Another account can rate the same song independently, producing a separate row with a different user_id.

Database results were checked in MySQL Workbench.
